# toto予測を確かめる方法

2026-11-02。研究用の評価方針と、ローカルで動く最小の集計コード。
予想精度や収益性を実証した結果ではない。

2026-11-15統合点検: ローカルの研究コードを独立した検証用として整理した。
確率の配列入力・余分な出目キー、前後に空白のある試合ID・回IDは、
誤採点や重複検査のすり抜けを防ぐため、黙って補正せず不正入力として扱う。

## 置き場

**World Toto Labの中で、予想を作る処理と、予想を確かめる処理を分けて持つ。**
totoの試合ID、締切、公式人気、候補、結果との対応を保てるため、
finance-executor-labへ分けるより、このリポジトリが適している。

| 内容 | 場所 |
| --- | --- |
| 共通の検証方針と実験の読み方 | この文書（`docs/research/toto-validation.md`） |
| 採点・較正・払戻集中度の純粋関数 | `src/lib/research/toto-validation.ts` |
| 手元のJSONを採点するコマンド | `scripts/validate-toto-research.mjs` |
| 実験ごとの仮説・対象期間・条件変更・結果 | 今後 `docs/research` に実験IDごとの文書を追加 |
| 元データ、取得本文、ローカルの集計出力 | Git管理外の `generated/research/<experimentId>/` |
| 締切前予測と公式結果の記録 | 既存の [toto-prediction-log.md](../toto-prediction-log.md) |
| 将来、採点結果を表示する画面 | 既存の `/practice-lab` を候補にする（今回未接続） |

`generated/` は再計算用の作業ファイルであり、恒久的な証跡の正本にはしない。
再現に必要な非機密の入力・出典・取得時刻・ハッシュ・コード版は、
内容と利用条件を確認したうえで実験文書から追える形で保存する。
原文の転載、個人別の購入情報、認証情報は共有リポジトリへ入れない。

## 参考記事から取り入れること

参考: こざま「[競馬AI頓挫記念。](https://note.com/pecofan/n/n2dfb3f66f0b4)」
（2026-10-29公開、2026-11-02確認）。著者自身の研究報告として扱う。
記事は、小標本での好成績、未来情報の混入、確率の過信、高配当への依存、
条件を繰り返し変える探索の問題を挙げ、事前に条件を固定する検証へ進んでいる。
競馬の成績や払戻率はtotoへ転用せず、以下はTotolab向けに組み立てる検証方法とする。

| 確かめたいこと | totoでの検証 |
| --- | --- |
| AIを加える意味があるか | 同じ試合・同じ判断時点の市場確率と、モデルを比較。公式投票率は群衆の比較軸として別に採点 |
| 買える時点の情報か | 各試合の開始時刻だけでなく、その回の販売締切より前に入力と予測が存在したことを確認 |
| 自信の強さが実現率と合うか | log loss、Brier score、確率帯ごとの予測平均と実現率。選抜した出目と公式人気20%以下の出目も別集計 |
| 数件の高配当に支えられていないか | 払戻上位1回・3回・投下した回の上位1%について、払戻寄与率と感度を表示 |
| 過去に合わせすぎていないか | 時系列で開発期間と未使用期間を分け、試した全条件を記録。条件変更後は別実験として将来分で評価 |
| 正しい払戻で評価しているか | 公式の等級別払戻との照合を優先。近似精算は別集計に残す |
| 市場間の差に意味があるか | 将来の別実験として、toto人気と外部1X2市場の時刻をそろえ、差の変化とその後の成績を比較 |

高配当依存が強いことだけで手法を否定しない。稀な当たりが重要な商品なので、
標本数と不確実性を併記し、将来も再現できるかを別途確かめる。
予測指標の改善と、控除・配当上限・当せん口数を含む回収率の改善も分けて判断する。

## 今回加えた集計

外部への接続や保存処理を持たない研究用コードで、次を計算する。

- 明記された時刻の順序、重複試合、確率の不備、未確定結果の確認。
  評価対象・保留・除外の件数と、除外理由を残す。
- モデル単独の指標と、市場・公式人気それぞれがそろう同一試合集合での比較。
  市場欠損を公式人気や均等確率で自動補完しない。
- 全出目、事前に選んだ出目、選んだ出目のうち公式人気20%以下の較正表。
- 回単位の回収率と払戻集中度。公式精算と近似精算を分け、全体値にも内訳を残す。
  候補なしの回はコスト0・払戻0で残せる。

予測行は、同じルール版による一つの実験・一つの評価期間を渡す。
別のルール版や、結果を見てから作り直した予測を混ぜない。
同じ実試合が複数のtoto回に現れる場合、共通の `matchId` で識別する。
この集計では重複した全行を除外し、評価したい一つの事前予測を明示的に選び直す。
払戻は一つの方式について1回1行に集約し、券ごとの払戻を独立標本として数えない。

### 指標の定義

- 出目はキー `"1" / "0" / "2"`。確率は0〜1で合計1（丸め誤差1e-6まで）。
  3キーだけを持つオブジェクトに限定し、配列や追加キーは受け付けない。
  百分率の変換、欠損補完、再正規化はしない。試合ID・回IDの前後の空白も許容しない。
- log lossは `mean(-ln(p_actual))`。対数計算に限り、確率の下限を1e-15にする。
  Brierは3出目の二乗誤差の和を試合平均する（3では割らない、範囲0〜2）。
  比較差はモデル値から比較対象値を引くので、負の値がモデルの改善。
- 的中率は最大確率の1出目。完全同率は `1 → 0 → 2` の順に選ぶ。
- 較正は固定の10確率帯 `[0,.1), …, [.9,1]`。
  全出目表は1試合3行になるが、独立した3試合を意味しない。
  選抜表は `selectedOutcome` の1出目だけを数え、各帯の件数も必ず読む。
  公式人気20%以下は固定の診断区分であり、選抜規則や利益の根拠ではない。
- 回収率は `払戻合計 / コスト合計`（1.0が100%）。コスト0では `null`。
  公式・近似の混合集計を公式精算の成績として扱わない。
- 払戻上位は投下した回の払戻総額で順位付けする。上位1%の回数は切り上げる。
  `payoutShare` は総払戻に占める割合（払戻合計0では `null`）。
  `zeroedPayoutReturnRate` は全コストを残して上位の払戻だけ0にする感度分析。
  `excludedRoundReturnRate` は該当回のコストも払戻も除く分析で、残コスト0なら `null`。
  両者とも、除外した世界で配当を再計算する反実仮想の市場シミュレーションではない。

### 実行方法

Node 24を使い、リポジトリ直下で実行する。追加依存は不要。

```powershell
node scripts/validate-toto-research.mjs scripts/fixtures/toto-validation.synthetic.json
npm test -- src/lib/research/toto-validation.test.ts
```

例のJSONはすべて架空で、実データや実績ではない。
入力形式は [合成例](../../scripts/fixtures/toto-validation.synthetic.json) と
[型定義](../../src/lib/research/toto-validation.ts) を参照。
実験用JSONの構造は `protocol / predictions / returns`。
出力は標準出力のみで、入力ファイルを書き換えない。
終了コードは0が集計完了、2が予測行の除外あり、1が入力・実行エラー。
0でも標本不足・全件保留・データなしはあり得るため、件数を見る。
JSONにも常に `assessment: "descriptive_only"` と
`profitability: "not_evaluated"` を出し、集計の成功を採用可否に読み替えない。

## 締切前の記録と実験条件

各実験の文書で、次を結果を見る前に固定する。

1. 仮説、比較対象、対象回・リーグ・期間、必要な標本数と終了日。
2. 学習データの最終時刻、コード版、ルール版、確率の作り方、選抜条件。
   開発用の過去データと未使用の評価期間を分ける。
3. 候補数・口数を比較する場合の同じコスト条件。候補なしや入力欠損を含める規則。
4. 販売締切より前の判断時刻、予測保存時刻、全入力の利用可能時刻、出典、試合IDの対応。
   2日目の試合のキックオフ前でも、toto締切後の価格は使わない。
5. 結果確定後の公式結果・等級別払戻の出典と照合方法。
6. 主指標、改善幅、期間別・リーグ別の確認方法、不確実性の評価方法と採否条件。
   同じデータで試した条件数と失敗・候補0件も記録する。

コードは `trainingDataThrough < frozenAt <= savedAt <= decisionAt < kickoffAt` と
`latestInputAt <= savedAt` を確認する。時刻はタイムゾーン付きISO形式。
`decisionAt` には実際の販売締切以下の時刻を入力し、`latestInputAt` は
市場価格、公式投票率、人力メモなど全入力の最も遅い利用可能時刻を入れる。
結果未確定なら `actualOutcome / resultConfirmedAt` は両方 `null` にする。
中止・不成立は通常の1X2結果に変換せず、別途記録・精算する。

**時刻をJSONに書くだけでは、締切前に存在した証明にならない。**
元スナップショットとその取得記録、コード版、変更を追える保存履歴を合わせて確認する。
後から作ったファイルのハッシュだけでは取得時刻を証明できない。
ルールの変更、選抜出目の差し替え、締切時刻、公式払戻の正しさは、この集計だけでは検証できない。
`returns` と `predictions` の自動照合も今回の範囲外で、実験文書で対象回を照合する。

## 次の実データ検証

未使用期間での評価、期間別の安定性、回単位の相関を考慮した区間推定、
多重探索の管理、元データ・公式精算との照合は未実施。
